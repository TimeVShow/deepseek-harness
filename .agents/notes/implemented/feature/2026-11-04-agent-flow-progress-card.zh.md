# Agent Note: Derive the Agent Flow progress card from run records only

Status: implemented

[English](2026-11-04-agent-flow-progress-card.md) | 中文

## Problem

一次运行的节点执行会开启各自的 Session，客户端会把用户带进正在对话的那一个。身处该 Session 时，没有任何东西把用户与运行连回：`FlowSelect` 只匹配运行的父会话 id，因此在途指示、流程面板与一切进度显示，都在用户坐进某个节点 Session 的那一刻丢失了该运行——而重载则让所有地方都丢失。当节点随后安静几十分钟（促使本卡片诞生的那次运行显示某节点在第二步停留了半小时），用户得不到任何信号，而几个诱人的兜底——把安静当作失败、自动重试、或显示编造的百分比——每一个都会捏造持久记录里不存在的状态。

## Decision

`packages/experimental/client-ui-agent-flow` 注册第四个输入框界面——`conversation.input.dock` 流程进度卡片，并由一个模块裁定所有会话相关显示可以声称什么：`run-view.ts` 从持久运行记录投影每一个事实，绝不出自组件内的推断。

关联规则是卡片与选择器共用的入口：一次运行涉及它的父会话与每个被节点执行记录为 `agentSessionId` 的会话。两个界面都通过该规则寻址会话，因此身处节点 Session 的用户保留指示与卡片，重载后仅凭记录即可恢复两者。

卡片只显示记录承载的内容，别无更多：阶段（运行中、等待你回复、已完成、失败、已取消）、已进行时长，每个正在执行或即将开始执行的节点一行，带轮次与它等待的存活前驱——被跳过的分支离开等待集，而节点的首次进入不等待那条只在后续轮次把运行路由回来的返工条件边——再加上唯一一次最近记录到的转变及其时间。运行超过可配置的 `stallNoticeMs`（默认十分钟）没有动静时，卡片提示最近已知活动；该提示不断言故障，因为记录安静并不构成故障的证据。名册读取失败期间，卡片把自身标记为最后已知状态并保留上一次的列表；下一次读取成功即清除标记。只有运行在运行中且其父会话仍有存活 agent 时才出现**取消**，卡片以运行自身记录的状态陈述结果——它绝不断言一次取消。

已结算对话的输入框收到的阻塞原因遵循同一纪律：仍有存活的执行后继时给出后继名，否则给出运行记录的结果。结构性 end 节点不是后继，因此已完成的运行读作已完成，而不是「仍在继续」。

## Testing

客户端测试覆盖父会话与节点会话的关联规则、存活优先排序、仅执行边的前驱与跳过出口、ready/waiting/settled 投影、轮次编号、阶段映射、活动时间并列与不可解析时间戳处理、冻结时钟下的安静阈值、恢复时清除最后已知标记、运行选择器、取消姿态持续到名册确认结算、取消失败的就地提示，以及 `stallNoticeMs` 的配置边界。

## Alternatives considered

**对安静的运行自动判定失败或自动重试。** 记录无法区分卡住的模型与一次漫长但正常的步骤；自动判定会捏造一次运行权威从未记录的失败，重试则可能重复副作用。卡片报告安静期，把判定——以及取消入口——留给用户。

**报告进度百分比。** 记录不承载任何总量估计；任何百分比都是编造的。带等待集的节点行恰好陈述已知的内容。

**把关联存储在 Session 上或经一个存活注册表。** 持久运行记录已经持有两个方向（`parentSessionId`、每个节点的 `agentSessionId`）；第二套存储会与它漂移，也无法在重载后存活。

**把输入框阻塞做成 toast。** 该阻塞是与界面绑定的状态，必须持续到运行结算，因此它像其他 composer 阻塞一样保持为持久的注册表条目。

## Consequences

卡片绝不对进度说谎，但它也无法解释一个安静的节点：它至多能说没有新的记录活动，而这正是诚实的边界。由其他客户端开启节点 Session 的运行仍能正确关联，因为规则读取的是记录，不是执行操作的客户端。`stallNoticeMs` 字段只是显示配置；它绝不能长成一个会判定运行失败的超时。
