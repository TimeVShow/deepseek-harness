# Agent Note: Disposal owns machine cancellation

Status: implemented

English | [中文](2026-11-06-disposal-owns-machine-cancellation.zh.md)

## Problem

Host teardown unloads every plugin fiber, and Cordis `_unload` (vendor/cordis/src/fiber.ts) runs a fiber's top-level effect disposers in parallel, each after one `await Promise.resolve()`. In the agent-loop plugin fiber, the `inbox` projection registration's disposer releases the factory's projection key concurrently with the FactoryOwnership disposer that cancels and drains every machine. An `Agent.cancel()` from an outside owner landing after that release — a subagent run abort fired by a sibling plugin's own unload, reaching `child.cancel({ kind: 'parent' })` while the child machine still drains — executed `inbox.clear()` against the released projection and threw `agent "<id>" cannot read inbox state: its projection registration is not active` from inside the abort listener. The throw originates in that listener, not in the caller: `AbortController.abort()` returns to its caller first and the process receives the exception afterwards (`abort returned > uncaughtException` on a minimal Node check), which is why callers saw an intermittent crash rather than a rejected call. The same parallel release also broke the disposal cancel itself: `machine.cancel({ kind: 'disposed' })` threw before aborting the phase, so the machine never drained and the held model request never settled. Failures were intermittent because the interleaving depends on which fibers the Host unloads in which order and how many microtasks each disposer chain consumes before another plugin's unload reaches its abort.

The first fix guarded the disposal cancel on the registration's liveness and passed `keepInbox` when the release had already removed the key, assuming the skipped durable clear was unobservable because the Session left with the machine. That assumption was wrong: closing the Session's write handle does not undo input already committed to its log. A later `resume` folds those `agent/inbox/spliced` insertions back into the inbox, and the next turn admits them into the model request. Unloading the loop while a creation listener held publication open — after that listener injected input — reproduced it: the resumed Session kept the message in `nextStep`, and the next model request contained the stale message beside the fresh one.

## Decision

Cancellation ownership transfers to disposal, and the transfer is code-sequenced inside the memoized machine `dispose`, not in fiber effects. `ReactLoopAgent.beginDisposal()` is the transfer: it latches a private flag and clears a latched wake on the active phase. `dispose()` calls it at its first synchronous statement, so every continuation the unload wave can schedule after the ownership disposer — including another fiber's executor abort — observes the transfer; the machineReady wait re-arms it when teardown outran the lifecycle effect minting the machine. `cancel()` with any cause other than `disposed` returns once disposal has begun; the disposal's own disposed-cause cancel still clears the inbox and aborts the phase. `runMaintenance`, `send`, and the wake latch keep their existing rules: wakes never latch behind a `disposed` reason, and input submitted after disposal begins remains the sender's bug with its existing error.

The disposal cancel no longer depends on the registration. `ReactLoopInbox` retains the pending lists it owns: it seeds them from the projection at construction and, after each durable splice, mirrors the committed event snapshot. The machine is the only writer for its Session, so the mirror stays exact, and `clear()` works after the factory's release. `dispose()` always cancels with the disposed cause and without `keepInbox`, and the durable discard lands while the Session write path is still open, so a resumed Session cannot replay input the agent never ran. A fresh inbox constructed after the release still fails loud, and crash recovery (no graceful disposal) still preserves legitimate pending input. `Agent.cancel()`'s Service Definition contract and the agent-loop README state the transfer.

Delivery closes with the same transfer. From `beginDisposal()` every public delivery entry rejects — `send` and its `followup`/`steer`/`inject` aliases, and the Inbox mutations — so a late external `inject` cannot commit the durable insert a resumed Session would replay; reads stay available to lifecycle observers. The machine's own tool pipeline keeps one internal delivery path (`appendInternal`): a tool result finalized while the machine drains still parks its context instead of losing it with the aborted turn. Teardown-aware callers recognize the exported `AgentDeliveryClosedError` to drop best-effort notices at that boundary — the subagent settlement path does — instead of reporting a transport failure. During activity, reads use the live projection while it is registered, so an observer of the committed splice event sees the new queue through both `agent.inbox.nextStep` and the projection before `append` returns; the retained mirror serves the release window, and a failed append publishes neither.

Effect-based ordering cannot own this seam. `sessionProjections.register()` creates its own top-level effect on the plugin fiber, so wrapping it cannot defer the release, and a wrapper disposer runs one microtask after the registration and loses to the synchronous release. Machine scope fibers are themselves top-level effects of the plugin fiber and unwind in the same parallel wave, and every fiber in the Host unloads transitively, so no fiber lifetime survives the machine drain to sequence it. Only the memoized dispose — plain code the ownership disposer invokes — can order the cancel-ownership arming against the release.

## Verification

`packages/core/agent-loop/tests/scope-lifecycle.spec.ts` pins the interleaving deterministically: a gated test tool keeps the turn in flight and the drain open, `loopFiber.dispose()` starts the unload wave, and after the wave releases the projection (asserted through `stateOf`) the test proves the teardown is still pending, then lands an outside `agent.cancel({ kind: 'parent' })` inside that window. The test also asserts every public delivery entry rejects there, the rejected identity never reaches the durable log, the cancel does not throw, no unhandled rejection is recorded, the turn ends `{ kind: 'aborted', reason: { kind: 'disposed' } }`, the machine reaches idle, and the unload completes. Against the pre-fix source the same test fails with the exact production error. `packages/core/agent-loop/tests/resume.spec.ts` pins the durable discard on all three ownership paths — per-agent handle disposal, factory unload after publication, and factory unload while a creation listener holds publication — with real JSONL persistence and a two-lifecycle resume: each asserts the stored log's canceled splice, an empty resumed `nextStep` for the injected identity, and that the next model request contains only the fresh message. It also pins the late-delivery window against persistence: an `inject` refused while a tool drains leaves no stored splice, and the resumed Session's next request carries only the fresh input. The accepted tool-result exception is pinned the same way: context a tool finalizes while the machine drains survives JSONL recovery in the resumed `nextStep` and enters the next model request beside the fresh input. `packages/core/agent-loop/tests/inbox.spec.ts` pins the public-mutation gate and the committed-read consistency: an observer of the splice event reads the new queue through both entry points. The crash-recovery control keeps pending input across a non-graceful lifecycle. The agent-loop suite, the subagent driver suites, and the web L1 acceptance group run green with the host-failure watchers (`unhandledRejection` and `uncaughtException`) asserting empty after every case.

## Alternatives considered

**Treat a released projection as an empty inbox in `stateOf`.** That swallows the illegal-lifecycle error for genuine stray access; `send()` after teardown is a sender bug that must stay loud.

**Catch and log the disposal-cancel failure.** The phase would never abort, the machine would never drain, and the held model request would leak. Fixing ownership is the review's principle; masking the read is not.

**Discard the inbox whenever a Session reopens.** That is indistinguishable from a crash to the resume path, and crash recovery must preserve legitimate pending input (a background inject is not stale work).

**Replay the Session log in the disposal path to recover the pending queue.** Synchronous historical reads are deprecated for new production calls, and the machine already observes every mutation it owns; the retained mirror needs no history scan.

**Retry or disable same-Session multi-run to hide the race.** The race belongs to teardown, not run multiplicity, and masking it would leave every teardown with an in-flight subagent at risk.

## Consequences

External cancellation is advisory while a machine tears down: only the disposed-cause cancel affects the machine, so the turn-ending cause during teardown is stable regardless of which outside aborts race it. Host and plugin teardown with in-flight subagent runs no longer produces the inbox projection error, disposal drains the machine even when the factory's projection release has already run, and the disposal durably discards pending external input so a resumed Session does not replay it. Context an accepted tool result finalizes while the machine drains is the remaining exception: it parks through the internal delivery path and stays pending for the resumed Session's next turn. Registration-like effects that must outlive a parallel teardown seam need the same code-sequenced ownership rather than reliance on effect order.
