# Agent Flow 独立插件整改计划

**交付目标**：另一位用户已有官方 DSH，在全新 Web profile 安装一个 Agent Flow 组合包，即可创建、运行、审查和找回流程。使用者无需修改、替换或重新编译任何官方宿主包。所有下游 Agent 对上游原件只有读取权，Reviewer 和返工节点同样受限。

**2026-11-08 执行状态（本轮）**：C 的插件路线已实现并在官方宿主通过正负对照：节点会话不可变的 header cwd 就是迭代目录（工作节点由每节点一个的 carrier 会话承载，交互节点直接记录），不需要修改官方 `subagent` 或 `sandbox-policy`。工作节点与交互节点各六种真实 Bash 写入全部被拒绝，上游原件保持不变。[实现与验收](references/standalone-verification-2026-11-08.md) A 完成；B、D、E 部分完成，剩余矩阵见该记录第 4 节。

## 接手基线

首个验证目标锁定为官方 `@deepseek-ai/dsh@0.2.2-rc.1`。取材分支为 `agentflow-0.2.2-rc.1`，本机位于 `/Users/lzy/Code/deepseek-harness-0.2.2`。本计划所在的交接目录也保留了旧宿主材料。实施时以官方发布标签和 0.2.2 移植分支为准。[官方发布标签](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-rc.1)

已有两份对照证据。四个候选包在官方 CLI 上走通过普通节点和刷新，但组合包为本机测试改写过依赖，官方宿主也没有 fork 的节点写权限接口。E26/E27 的拒写证据来自配套 fork。本次将这两个场景合并到同一组原样安装包、同一个官方宿主上验收。[候选包与宿主验收](references/package-and-host-verification-2026-11-08.md) · [只读交接验收](references/read-only-handoff-acceptance-2026-11-08.md)

## 派工顺序

| 任务 | 建议负责人 | 前置 | 交回什么 |
| --- | --- | --- | --- |
| A 固定官方对照和复现 | 集成人员 | 可立即开始 | 可重复创建的官方测试环境、宿主依赖清单、当前包的失败证据 |
| B 去掉原生会话占用依赖 | Flow 服务与客户端人员 | 可与 A、C 同时做设计；用 A 的环境验收 | 插件自有运行历史、负向身份测试、保留或调整的入口说明 |
| C 在官方宿主验证只读交接 | 执行器与沙箱人员 | 先做最小探针，再决定正式实现 | 可执行的允许与拒绝用例、适用范围、插件实现或上游缺口结论 |
| D 从官方基线组合候选 | 包与发布人员 | B、C 的可行路线确定 | 干净候选分支、四包原样 tarball、用户安装步骤 |
| E 独立签收 | 未参与实现的验收人员 | A–D 的同一候选版本 | 安装记录、权限与行为矩阵、发布或阻断结论 |

### A · 建立不依赖 fork 的基准

1. 记录官方标签、移植分支当前提交、工具链、四个插件包版本。在移植工作树执行 `git diff --name-status dsh-v0.2.2-rc.1 HEAD`。将差异分成四个 Flow 包、宿主产品代码、测试支持、仓库登记与文档。重点核对 `api/session-controller`、`client/ui-workspace`、`core/session`、`sandbox-policy`、`subagent` 及其 provider。
2. 在插件仓库外建 consumer 目录，使用全新 `DSH_HOME` 和精确版本的官方 CLI。保存 CLI、Session Controller、sandbox-policy、subagent 及实际 provider 的解析路径和版本，确认没有工作区链接、依赖覆盖或 fork 构建产物。权限探针使用临时的合成文件，不接触真实运行原件。
3. 用候选包分别运行普通节点、交互节点和写入上游的反例。记录是启动失败、写入被拒还是意外写入成功。旧实现的普通 worker 会传 `sandboxRoot`，交互节点会调用 `sandboxPolicy.setRoot()`，两个入口都要测。保存失败用例，供 C 原样重放。

### B · 让运行身份和历史归插件所有

1. 在四包内定位 `sessionUsage`、`occupied`、运行列表、取消和结束澄清的消费者。优先复用已有运行记录的 `runId`、`parentSessionId` 和归属校验。面板从插件持久化记录列出历史，操作定位到选定的 run，并校验调用者有权操作。不要仅凭 runId 放开取消权限。
2. 原型先支持面板启动、刷新找回、打开原结果、取消、回到交互节点。明确处理父聊天仍为空白、官方「新会话」复用它的情况；仅把 UI 搬到面板无法解决两个逻辑会话共用一个底层 ID 的串用。可试验插件管理的专用运行会话或其他公开的身份机制。composer 快捷入口可以保留，但要经过同样的隔离用例。
3. 用同工作区两个聊天、同聊天两个 run、切换新会话、归档和重开验证。确认没有旧卡片串入、历史丢失、取消错误 run；历史数据升级用副本测试。如果官方接口无法同时保留原生侧栏历史和身份隔离，列出用户会失去的具体行为，交产品负责人取舍后再调整入口。

**完成判据**：在原版 Session Controller 和工作区 UI 上通过上述用例，插件无需宿主识别 `occupied`。需要保留的原生侧栏能力若只能通过上游扩展提供，单列到上游提案。

### C · 先验证可执行的权限方案

1. 用「Writer 产出原件 → Reviewer 读取并尝试覆盖 → Reviewer 在本轮目录写报告」建立最小探针。覆盖文件工具和 Bash 子进程。把相同字节写回也要收到明确拒绝；同时验证 Reviewer 可以读取、复制到自己的目录、运行构建、写报告。记录写入返回值、进程退出码和原件完整性。
2. **优先试官方能力。** 验证插件能否创建独立节点执行环境，以节点迭代目录作为实际可写根，将上游材料只读提供给它。分别追踪工作节点、交互节点、派生子 Agent 和会话恢复。单独验证工作区成员关系、相对路径和取消清理。仅切换 `cwd`、复制后仍能按原绝对路径访问原件、提示词约束、事后比哈希，都不能充当权限实现。
3. 如果现有 provider 无法隔离，评估插件通过公开执行器接口提供自己的隔离后端。复用可维护的沙箱实现，确认文件工具、shell、终端等有效写入通道接受同一权限限制。先核对该路线对交互会话和目标平台的影响，再扩大实施。
4. 对可行路线补全反例：覆盖、删除、重命名、原子替换、符号链接别名、返工时篡改上一轮文件、嵌套委派绕过。检查上游目录落在系统临时区、额外可写根或父会话授予宽权限的情况。无法安全支持的配置必须在启动受影响节点前报错，用脚本模型断言该节点请求数为零。

**决策点**：若官方宿主上的候选路线通过正负对照，再替换 `executor.ts`、`conversation.ts` 对 fork 专有 API 的依赖。若两条路线都无法安全实现，交回最小复现、缺少的通用能力、受影响的宿主版本和上游提案。保留已验证的 fork 路径供内部使用；等含所需能力的官方版本发布后，再对该版本做独立安装验收。

### D · 重新组合可分发候选

1. 从官方标签建立候选分支，迁入四个 Flow 包及其必要的测试和构建登记。按 A 的清单逐项核销宿主产品差异；后续上游提案单独维护。保留现有 fork 作为对照，避免在原分支一次性删除改动。交接材料所需的仓库检查豁免与发行包无关。
2. 对插件的宿主导入、类型声明和 UI 注入从源码追到发布产物；在纯官方依赖下做类型检查和启动检查。旧 fork 写有必读 `sandbox/root` 事件的 Session 应单独验证兼容范围，保留原始记录，不通过删事件让旧宿主读取。
3. 选择团队有发布权限的包名和 scope，核对四包间依赖与宿主 peer 范围。用正式打包流程生成 tarball 和校验值。可在隔离测试 registry 提供同一组原样包，按面向用户的方式只安装组合包，由包管理器拉取其他三包。此项验收无需公开发布。

### E · 最终签收单

| 必验项 | 通过证据 |
| --- | --- |
| 用户安装 | 新目录、全新 profile、精确官方 CLI；一次安装组合包。记录依赖树和四包校验值；没有本地链接、事后改包、宿主替换或兼容性豁免。 |
| 运行和归属 | 从用户入口运行普通及交互 Flow，刷新能找回；同工作区切换会话及多 run 时卡片、结果、取消和文件预览均指向正确身份。 |
| 上游原件只读 | 在同一安装环境运行 C 的允许和拒绝用例，附实际工具结果。fork 通过而官方环境失败时，此项记为失败。 |
| 调度和交付回归 | 三角色实际并行后只汇总一次；串行下游收到正确产物；同一条件连续退回两次后第三轮成功。保留不同 run 同名文件的预览测试。 |
| 支持范围和恢复 | 记录实测宿主、平台、provider、权限配置和已知限制；验证卸载后宿主仍能启动。对带历史数据的配置使用副本验证，注明可读取的记录范围。 |

**发布决策**：A–E 在同一官方宿主和同一组候选包上满足上述两项交付目标，方可标注「可独立安装」。否则列出失败用例、责任组件、下一步和当前可支持的范围。提交结果时附实际执行命令、退出码、候选标识和脱敏日志位置，区分已验证、失败与未验证。
