# Agent Flow 阶段性端到端测试计划

日期：2026-11-05。状态：待实施/执行的测试计划；本轮已执行的复验与并行探针见 [检视报告](flow-isolation-recheck-2026-11-05.md)，不能将本计划表格记为测试通过。

## 测试目标与边界

检验用户能否完成任务、理解当前状态、找到本次结果，并在新会话、多次运行、多 Flow、并行、失败和刷新时保持身份与数据正确。质量、模型路由、执行结果、成本观测分别记录；不以低 token 消耗代替任务完成，不以模型说“完成”代替文件和运行事实。

必须区分四个身份：工作区 workspace、会话 sessionId、图定义 flowId、一次执行 runId。同名 Flow 可能有不同 flowId；同一 Flow 每次执行必须有新的 runId。同工作区不构成结果关联，两个 run 不能仅凭 flowId 合并记录。

默认结果关联保持现有规则：运行父会话及该运行明确记录的节点会话可见；其他会话不可见。全局 Agent Flow 历史页可列出所有运行，但进入具体会话后的卡片不能借用全局选中状态。

本轮验收前置：修复 FSI-002 的历史列表呈现、FSI-003 的持久使用记录回填与保留。未修时相应用例应如实红灯，不能通过隐藏旧会话绕过。

## 三个可重复使用的 Flow

所有节点都要求在最终说明中保留本次 CASE 标识，产物只写指定节点目录；多个节点可故意使用相同文件名 RESULT.md，测试必须按完整资源地址和 runId 区分。执行线自动带前驱结果；原用户需求只通过显式 Start 输入线接入。不要给已有执行线再次画冗余输入线。

### F-A：双节点简报（最便宜的基础冒烟）

执行图：Start → Writer → Checker → End；另加 Start → Writer 的输入线。Writer 生成一份简报与 RESULT.md，Checker 核对简报中所有要求并写自己的 RESULT.md。没有 interactive 和 condition，不要求普通节点凭空输出路由词。

输入示例：`[CASE:A1-7F31] 为“社区图书交换”活动写一份短简报，必须包含地点、开放时间、借还规则三部分。请在最终说明和文档中保留 CASE 标识。`

第二次输入：换成 `[CASE:A2-9C82]` 和“办公室午餐预订”，内容要求改成截止时间、取消规则、联系人。断言 A2 的结果不含 A1 的独有标识或旧活动内容。

### F-B：设计、实现、审查（不同业务 Flow + 串行返工）

执行图：Start → Clarify → Design → Implement → Review → Condition；approved → End，rework → Implement。Start → Clarify 为输入线；Design → Review 为额外输入线，使 Review 能比较设计与实现。Design → Implement 已有执行线，不再加冗余输入线。

Clarify 为唯一 interactive 节点，明确确认需求及是否开始；最终输出需求文档并以 `Result: done` 结尾。Review 正确使用 `Result: approved` 或 `Result: rework`。自动化夹具固定第一次 rework、第二次 approved，避免靠真实模型随机找出问题触发回环。真实模型用例只判实际审查行为，不要求为了测试强行报错。

输入示例：`[CASE:B1-48D2] 设计并实现 Python 排序模块，仅包含冒泡排序和归并排序；支持空数组、重复值、负数；提供可运行测试和设计说明。`

模型可按角色配置：Clarify/Review 使用主力模型，Implement 使用执行模型。记录实际请求的 provider/model，不能只看选择器标签或模型自称。maxIterations 当前限制的是总 Agent 执行次数，不是循环轮数；给测试图设置足够的上限，例如 16。

### F-C：多人需求评审（当前可实现的“会议”）

执行图：Start → Host（interactive）→ Product / Engineer / QA 三路并行 → Summary → End；三路均直接连到 Summary，默认 all 汇合即可。Start → Host 加输入线。

Host 输出共同确认的需求；三个角色分别产出用户价值、技术方案、风险与验收标准；Summary 根据三份结果给出共识、分歧和后续行动。角色的不同模型通过不同 Agent 模板配置。每个角色只能写自己的指定目录，不能争写同一个项目文件。

输入示例：`[CASE:C1-5A06] 评估一个社区活动报名系统：最多 100 人，支持候补和取消。产品、工程、测试三个角色分别给出建议，然后汇总共同结论与分歧。`

当前没有实时聊天室广播：三路第一次分析互不读取兄弟节点的未完成输出。若要互相补充，增加固定第二轮：Summary-1 → Product-2 / Engineer-2 / QA-2 → Summary-2 → End。第二轮节点收到第一轮汇总再分析；这是展开的 DAG，不是循环内部并行。不要把“共享即时消息房间”或“任意轮次自动讨论”列为当前支持项。

## 执行层级

| 层级 | 环境与方法 | 能证明什么 |
| --- | --- | --- |
| L1 无 key 完整链路 | 测试专用 profile/overlay 启动真实 DSH、Remote、composer、Flow service、调度器、Session 和文件侧栏；仅模型端替换为可控脚本 | 确定性的身份、调度、交接、取消、故障和 UI 行为 |
| L2 浏览器验收 | 在 L1 真实服务上点击编辑、选择 Flow、输入、切会话、展开结果、预览文件；保存截图/GIF | 真正的组件装配、会话切换、布局和交互；不以 jsdom 替代 |
| L3 真实模型冒烟 | L1/L2 通过后，用户选定模型运行 F-A/F-B/F-C 少量样本 | 模型适配、任务交付质量、实际延迟及费用；不拿它排查可确定性的 UI 逻辑错误 |

所有产品进程通过 dsh profile 启动。浏览器目录选择自动化采用仓库规定的 `pnpm dsh web --patch apps/web/tests/pin-browse-picker.overlay.yml`；脚本模型通过额外测试 overlay 接入，不能把测试 provider 写入正式默认配置。自动化使用独立临时工作区与存储根，不操作用户历史运行。当前已有 StubProvider 运行时测试可复用脚本思路，但其手动装配/假根 Agent 本身不等于 L1 已完成。

并行测试用显式闸门：等所有应并行的请求都启动后才允许它们完成；不能只比较总耗时或只看三个节点都显示 running。会话恢复、存储拒绝、断线、慢流同样使用可控事件而不是依赖睡眠碰时序。

## 身份与使用组合矩阵（首批必测）

本表必须在真实 New Session 按钮、真实 Flow 选择和提交入口执行，不能只给组件传一个新的 sessionId。

| 编号 | 场景与操作 | 关键验收 |
| --- | --- | --- |
| E01 | S1 跑完 F-A；点新对话到 S2，不选 Flow | S2 是不同身份且没有旧卡片；S1 仍在历史列表，返回可见原结果；刷新重复检查 |
| E02 | S1 跑 F-A(A1)，S2 跑同一个 F-A(A2) | flowId 相同、runId 和父 sessionId 不同；输入、结果、文件、模型请求标识不串；S1/S2 互切正确 |
| E03 | 同一 S1 连续跑 F-A(A1)、F-A(A2) | 两条 run 记录均保留，同会话运行选择器能分别查看；新运行不覆盖旧运行，默认选中规则可预测 |
| E04 | S1 跑 F-A，S2 跑不同 F-B | 图、节点名、结果与模型路由各自对应；从 F-B 进入 F-A 历史后再返回 S2 不显示 F-A 卡片 |
| E05 | 同一 S1 先 F-A、再 F-C | 同会话可查看两种 Flow 的独立运行；选中的图不会误用上一次图/角色/需求；退出选择后普通消息仍是普通对话 |
| E06 | S1/S2 并发跑相同 F-A（不同 CASE） | 两个 run 同时存在；取消 S1 的运行只影响它；S2 完成；刷新、列表和文件入口保持各自身份 |
| E07 | S1/S2 并发跑不同 F-B/F-C | 澄清回复、结束澄清、取消和汇总均作用于目标 run；自动导航不把回复提交到另一个运行的交互会话 |
| E08 | 同一 S1 并发启动两次同 F-A；再在另一工作区重复 F-A | 同父会话中按 runId 选择和取消，不按 flowId 批量作用；跨工作区结果和资源地址不串。若产品决定禁止同会话多运行，应明确拒绝，不静默合并 |
| E09 | 克隆 F-A 为不同 flowId 但相同显示名；分别运行 | 名称不作为记录主键；界面提供足够信息辨认两次运行，运行快照/路径正确 |

每行核对原始 request.input、父 sessionId、runId、节点 agentSessionId、节点 inputs 的 nodeId/iteration、真实模型请求和文档内容。只检查页面出现“完成”不算通过。

## 并行、交接与回环

| 编号 | 操作 | 关键验收 |
| --- | --- | --- |
| E10 | F-C 三个分析节点均被闸门阻塞，maxConcurrentAgents=3 | 三个请求在任一个完成前全部启动；Summary 请求数为 0；逐个释放，全部有效前驱完成后 Summary 只启动一次，包含三个正确来源 |
| E11 | 同图并发上限分别为 1、2、3；再同 Flow 同时跑两次 | 单次 run 峰值不超过配置；当前上限是每 run，两个 run 的总峰值可超过该数，不把它误记为全局限流；取消排队节点不会随后启动模型 |
| E12 | 比较三路直接接 Summary 与显式 all → Summary | 两者合并来源等价；不存在重复交接或漏分支；先完成的分支不能提前启动 Summary |
| E13 | 条件只选择一支，未选分支与已选分支汇合 | 未选分支为 skipped，汇合只等待有效前驱；无全部跳过却凭空启动的工作节点；终态能收敛 |
| E14 | F-B 第一次 rework、第二次 approved | 设计结果可复用，刚完成的审查意见到达返工入口；实现/Review 严格取本轮；结束后没有残留 running；条件节点不出现在结果卡片，真实结论保留 |
| E15 | F-C 增加固定第二轮；另尝试保存“循环内并行”图 | 展开 DAG 可执行，第二轮读取第一轮汇总；循环内并行在保存/启动前明确拒绝，不能产生付费请求 |
| E16 | 删除 Start 输入线、加入无保证可用的输入源、制造非法 Result | 无 Start 输入线时模型不得默认获得原始用户消息，界面有清晰提示；非法输入依赖保存时拒绝，持久坏记录运行时也不能凭空补值；非法 Result 使对应节点/run 失败并说明原因 |

角色之间读写同一项目文件不由 DAG 自动隔离。并行用例给每个角色独立目录；若要测试共享代码修改，应先约定文件所有权或隔离工作树，不能声称现有 run 目录已解决所有代码写冲突。

## 会话生命周期、失败与持久性

| 编号 | 操作 | 关键验收 |
| --- | --- | --- |
| E17 | F-B 澄清多轮，在用户回复后模拟长 reasoning 和工具运行 | 状态从等待用户变成处理/推理/工具执行；有活动不能误报卡死；新对话不继承旧运行；当前运行入口仍可找到 |
| E18 | F-C 一个分支抛错，另一个慢执行、第三个排队 | run 失败原因指向真实节点；其余运行时自有工作收敛，Summary 不执行；不会后台继续产生无人可见的请求 |
| E19 | 模型慢流、网络断线、恢复；在三个阶段取消 | 显示“活跃生成 / 无新活动 / 观测中断”的真实区别；取消有反馈，终态稳定；重连不重复启动节点。新请求前、流式中、等待汇合均覆盖 |
| E20 | UI 刷新；单独模拟 Host 重启 | 刷新恢复已有 run 与会话关联，不重跑；Host 重启按当前中断收敛策略显示失败/中断，不声称断点续跑成功，不能偷偷再发模型请求 |
| E21 | 旧运行无 usage 行 → 重载 → maxRuns=1 清理旧 run → 再重载；再注入首次 usage 写失败 | 占用资格不丢失、旧会话不再被新对话复用；唯一持久依据未安全转存前不得删掉。此例当前失败，修 FSI-003 后执行 |
| E22 | 切新对话后在分组、平铺、搜索、归档列表找旧 Flow 父会话 | 旧会话仍是有业务历史的可识别行，不变成“新对话”，不因 blank=true 被隐藏；恢复/打开旧会话不新建替代身份。此例当前失败，修 FSI-002 后执行 |

## 用户实操推荐顺序

先用短 F-A 验证，再使用 F-B 的代码任务。每一步记下界面运行标识与 CASE，发现身份串用立即停止后续付费测试。

1. **E01**：新建 S1，跑 F-A(A1)；完成后点新对话，检查旧结果消失且 S1 仍可返回。刷新后再做一次查看。
2. **E02 + E03**：S2 跑同 F-A(A2)，互切 S1/S2；然后在 S2 再跑 F-A(A3)，确认两次 run 分开可选。
3. **E04 + E05**：S3 跑 F-B(B1)；S2 改跑 F-C(C1)，检查不会沿用上次图、需求或文件。
4. **E10**：F-C 明确确认开始后，观察三个角色活动及最终汇总；普通人工观察仅为体验证据，严格并发断言由闸门自动化补齐。
5. **E06**：两个会话同时跑短 F-A，取消一个，另一个正常完成。用不同 CASE；不要让两个代码 Agent 同时改同一个源码目录。
6. **E14 + E24**：检查 F-B 的审查与返工、结果文档，打开 Markdown 和相对链接；切新对话再返回，确认结果、历史轮次、文档仍在正确位置。

## 自动化交付拆分与通过标准

- 第一批：E01～E09、E21～E22，先保护身份、历史和持久性；包含真实 composer 提交与 New Session 导航组合。
- 第二批：E10～E20，脚本模型可控地验证并发、回环、故障、刷新和中止；保留本轮已通过的两个运行时探针作为可复用回归素材。
- 第三批：E23～E25 与 L2 浏览器演示；随后做 L3 真实模型任务质量验证，接入既有 T-10 验证目标。

测试结果每项填写：代码版本/环境、flowId、sessionId、runId、CASE、预期、实际、状态（通过/失败/未执行）、证据路径。失败附首个不符合预期的事件或请求，不导出凭据、请求鉴权头或完整推理正文。

验收必须同时满足：所测任务有真实产物；运行终态与节点终态一致；输入和结果无串用；预览资源属于目标运行；失败与等待状态可理解；过程可从会话/运行记录追溯。真实模型阶段另外记录输入/输出 token、耗时与账单数据（数据存在时），以及设计一致性、测试通过与审查有效性，不以单个模型自评作为质量通过依据。

这份计划不是已完成工作的证明。只有 L1、L2 对应场景都实际执行并留证据，才标记端到端通过；纯函数/组件/运行时测试通过只计入它们各自覆盖的层级。
